## 1. Facts the design stands on

1.1 **A column is 27 chunk rows.** `WorldGenerator` (worldgen.cpp:201) sets `topChunkY` from `max(baseHeight + amplitude + 400, seaLevel, baseHeight + towerStoreys * 56 + 200)` = 1720 voxels: rows 0..26, 1728 voxels, 108 m. `ChunkStreamer::launch` (streaming.cpp:27) builds every row of a column in one job; `generateTerrainChunk` returns at once for rows above the terrain (worldgen.cpp:64, `fy(oy) > top`) and makes a uniform stone chunk for rows well below it (66). Empty chunks are not kept (`!c->empty()`). The nightly log of 2026-10-18 says: radius 36 = 5,329 columns, 40,326 chunks (7.6 per column), 24,014 of them uniform (4.5 per column), 6.23 M bricks, 148.8 MB brick pool, 1.6 s to load on 7 threads. So a column costs about 3 bricked chunks (the terrain band) and 4 or 5 uniform ones (32 bytes each, no pool memory), and about 28 KB of pool.

1.2 **The GPU record table is sized for the whole column window.** `levelCfg` (main.cpp:918) sets `dirDims = {win, topChunkY + 1, win}` with `win = 2 (radius + margin) + 2 = 78` and `maxChunks = 78 x 78 x 27 = 164,268`; gpu_world.cpp:27 allocates `maxChunks x kChunkRecordWords x 4` = 164,268 x 2,128 B = **350 MB** of device memory for level 0 at radius 36, whether or not the chunks exist. That is the number a vertical window would cut (5.4), not the brick pool.

1.3 **Residency is by column** (`loaded_` keyed by `key(cx, cz)`, streaming.cpp:18), and so is everything around it: `World::residency` (16: `OutOfWorld` for y outside 0..topChunkY, `OutOfMap` beyond the map edge, else by the column), `adoptColumn` (56: fills the empty rows with deferred edits), `saveAll` (82), `evictColumn` (109), `stateHash` (227: the sorted column keys and the store's content), `LodUpdater::edited_` (lod_updater.hpp:50: by column then height), the lockstep `pending_` (a column requested at tick T is adopted at T + 30). `rebuildQueue` (144) walks a square and sorts by squared distance to the nearest centre: the request order is already by distance; only the *membership* is a square (`cheb`, 125).

1.4 **The generator is a pure function of (params, chunk coord)** with a per-column sample cache `GenColumn` (worldgen.hpp:44: 4,096 heights and jitters) and a pre-built, world-wide list of feature ops routed per chunk (`ops_`, `opsByChunk_`, worldgen.cpp:300..315). The feature loops run over the whole map at construction (trees on a 112 voxel grid over `W x D`, 213): an endless world cannot pre-build them. The far levels (`level` 1 and 2) scale the big ops and drop the small ones (`scaleOpToLevel`, 165).

1.5 **Integer noise is safe far out.** `fbm2` shifts x by 6..11 bits (worldgen.cpp:17..20) into an `i32`: a wrap happens at |x| >= 2^20 voxels (65 km) for the finest octave and is a harmless repeat of the noise, not a crash; `hash3` takes `i32`. `IVec3` voxel coordinates are `int`, so the world is addressable to 2^31 voxels (134,000 km). `chunkOf` is an arithmetic shift (world.hpp:112): negative coordinates work.

1.6 **Float positions.** The player (player.hpp:116 `Vec3 pos_`, metres), bodies (body.hpp:43 `Vec3 pos`, metres), agents (agent_system.hpp:75, voxel units), vehicles (vehicle_system.hpp:13, metres) are `float`. The camera is `DVec3` (renderer.hpp:34) and the GPU works relative to the level-0 window origin (renderer.cpp:735..739): rendering already has a floating origin. Liquids, fire, drops' landings, events, prefab instances are integer voxels.

1.7 **Journal-free edits exist in three flavours** (destruction_system.cpp): `liquidEdits_` (168, with the `SideRecorder` so an undo takes the flow back), `fireEdits_` (137, same), `cosmeticEdits_` (111, no journal, no side: settled grains; off while recording because the GPU decides them). Wear wants the fourth flavour: **no journal, no side, but deterministic** (D4). `Transaction.system` (txn.hpp:11) only matters for journaled batches.

1.8 **Hash and replay.** `sessionHash` (main.cpp:2230) mixes the world content (or a box of it), the bodies, gravity, drops, vapor, fire, the deferred edits, the streamer, the liquid totals, the events, the emitters, the store, the grab, the vehicles, the agents and in a net session the players. The replay header carries `seed`, `world`, `terrain`, `radius`, `spot`, `hash_radius`, the script, the materials, the store id and `players` (main.cpp:527..537, 630, 2779). `world` is read with `atoi` (489): "endless" must be parsed before `atoi` sees it.

1.9 **Rain is the pattern for weather.** `fx.rain` is a logged action `rain` (main.cpp:1428 `rainOn = at(0) > 0.5`), the simulation reads `rainOn` (2680: `drops.rain`). `fx.snow(amount, falling)` is render-only (lua_host.cpp:1053, `coverSnow`, `coverSnowFalling` at main.cpp:727). The real snow needs the `falling` flag in the simulation: a logged action `snow` with the same shape as `rain` (3.4).

1.10 **The cover follows the voxels.** The ground pass picks a type by the surface material (foliage_ground.comp:164: nothing stands on a material with no entry); `coverTints` has an entry per material. A voxel that turns from grass into dirt loses its blades and its far tint at once, for free. Exception: a **painted** type grows on any ground (foliage_ground.comp:104); 2.8 handles that.

1.11 **The soak's journal growth.** `Journal::trim` (journal.cpp:38) drops whole groups while `retained_ > cap_`, where `retained_` counts **slots** (`retainedBricks`, txn.hpp:15) and `cap_` is 250,000. A slot is 8 words (class 0) or 516 words (class 5, brick_pool.hpp:14). The fire scenario rewrites bricks with many palette entries (ember, char, air, grass, dirt, leaves: class 3 or 4, 88 or 392 words): 250,000 x 392 x 4 = 392 MB before the cap bites, which is exactly a brick pool that grows for hours. The `SideRecorder` is closed at `cap / 8` **bricks** too (destruction_system.cpp:104). D20.

## 2. (2) Wear and paths: the simulation side

### 2.1 Data

`WearTable` in `src/sim/wear_table.{hpp,cpp}` (a CSV reader of the comment-keeping kind of `loadCoverCsv`; the window and the MCP tools come later, the file first):

```
# wear.csv: what walking, driving and lying on a surface does to it, and what the walkers carry away
# from, to, who, radius, threshold, decay, regrow, regrow_to, falling_refill, pickup, deposit, track, fade, wash
grass,  dirt,   players;agents;vehicles;bodies, 0.20, 120, 0.02, 36000, grass, 0,   0.00, 0.00, none, 0,    1
dirt,   path,   players;agents;vehicles,        0.20, 600, 0.00, 0,     ,      0,   0.60, 0.00, none, 0,    1
snow,   sink,   players;agents;vehicles;bodies, 0.25, 6,   0.00, 0,     ,      1,   0.80, 0.00, none, 0,    1
concrete, ,     ,                               0,    0,   0,    0,     ,      0,   0.00, 0.50, mud,  3600, 8
stone,  ,       ,                               0,    0,   0,    0,     ,      0,   0.00, 0.40, mud,  3600, 8
wood,   ,       ,                               0,    0,   0,    0,     ,      0,   0.00, 0.60, mud,  2400, 8
```

| column | meaning |
|---|---|
| `from` | the surface material (the top solid voxel under the walker) the row is about |
| `to` | the material it becomes at `threshold`; `sink`: the top voxel is removed (snow); empty: the row is a tracks row only |
| `who` | which sources wear it: `players`, `agents`, `vehicles` (wheel contacts), `bodies` (awake bodies in contact with the world, moving faster than 0.2 m/s) |
| `radius` | metres: the disc of cells each stamp touches (0.20 = a foot; a wheel uses its width, a body its contact points) |
| `threshold` | stamps (weight 1 at the centre, falling to 0 at the radius) until the cell changes |
| `decay` | per second, how much a cell's counter loses while nobody steps on it (0: never) |
| `regrow` | ticks after the last stamp until a changed cell goes back (`regrow_to`); 0: never |
| `falling_refill` | snow: 1 = a sunk cell gets its voxel back while it snows (one voxel per `threshold` ticks) |
| `pickup` | 0..1: how much `load` a walker gains per step on this surface (mud from dirt and grass when wet, snow from snow) |
| `deposit` | 0..1: how much of the walker's load one step leaves here (concrete, stone, wood: the hard floors) |
| `track` | the paint palette entry the deposit paints (docs/PAINT.md: `mud`, `snow-track`, `sand`); `none` |
| `fade` | ticks until a deposited voxel goes back to its old paint (the walker's load decides how dark the print starts: paint only when load x deposit >= 0.05) |
| `wash` | how much faster the fade runs while it rains |

A material that is in no `from` is untouched. `path` is a new built-in material (`mat::Path`, a trodden earth colour, `coverTints` has no cover for it) so a path shows without the cover table knowing; projects with their own materials name their own. Unknown material names are reported and the row is skipped (the pattern of `packCover`). Ranges are a `wearColumns()` table like `coverColumns()`.

### 2.2 State

```cpp
struct WearCell {           // one 2 x 2 voxel cell of the ground, keyed by (x >> 1, z >> 1) and the y of the top voxel when first stamped
    u16 count;              // stamps so far (fixed point: 1 stamp = 16)
    u16 lastTick;           // low 16 bits of the tick of the last stamp (the decay and the regrowth clock, with the system's own tick)
    u8  rowIndex;           // which wear.csv row applies (so a cell that changed knows what to regrow to)
    u8  sunk;               // snow: voxels removed so far (what refill may put back)
};
struct TrackVoxel {         // one painted voxel of a track
    IVec3 pos; u8 prevState; u8 track; u16 bornTick;
};
class WearSystem {
    std::unordered_map<u64, WearCell> cells_;   // bounded (D7)
    std::vector<TrackVoxel> tracks_;            // bounded (max_tracks, default 32,768 = 0.5 MB), a ring: the oldest is restored first when full
    struct Walker { u32 id; float load[3]; };   // load per track class (mud, snow, sand); players by slot, agents and bodies by id, vehicles by wheel
};
```

Memory: 65,536 cells x 8 B in a map is about 2.5 MB with the node overhead; use `std::unordered_map` for the first version and switch to an open-addressing table if the profile says so (it will not: 256 lookups a tick).

### 2.3 The step (`WearSystem::step(tick, sources) -> std::vector<VoxelEdit>`)

1. **Collect stamps** (main thread, before the physics step, where `agents.tick` runs, main.cpp:2695): for every simulated player (`simPlayers` in a net session, `player` otherwise: never the live local player in net mode) that is `grounded()` and moved more than 0.02 m since its last stamp: a stamp at its feet; every agent on the ground the same; every vehicle wheel with a contact; every awake body with a world contact moving faster than 0.2 m/s: a stamp per contact point (at most 4 per body). Sources are visited in a fixed order (players by slot, agents by id, vehicles by id, bodies by id) so the per-tick cap cuts deterministically.
2. **Find the surface**: `world.topSolidBelow(x, z, feetY + 2, feetY - 12, y, v)` (world.hpp:75). `Unloaded`: skip (nothing is known there; in a net session every peer has the column, by the lockstep rule). Liquids: skip.
3. **Stamp**: the cells inside `radius` get `count += 16 x weight`; a new cell is inserted only if the map has room (D7: when full, first the sweep, then insert; if still full, the stamp is dropped: the cap is absolute). Table row by `from = material(v)` and `who` contains the source class.
4. **Threshold**: a cell at `count >= threshold x 16` whose top voxels are still `from` emits the edits: for `to = material`: `VoxelEdit{(x, y, z), makeVoxel(to) with the voxel's texture byte kept}` for the up to 4 top voxels of the cell (each column's own top: a slope has them at different heights, found with `topSolidBelow` per column, bounded to 4 reads); for `to = sink`: the top voxel becomes air, `sunk += 1`, `count = 0` (the next voxel needs `threshold` again). The cell's `count` is reset to `threshold / 2` so decay and regrowth have a meaning after the change.
5. **Decay and regrowth** (a slice: `cells_.size() / 64` entries per tick in key order, so every cell is visited about once a second): `count -= decay x 16 / 60 x elapsed`; a cell at 0 that never changed is erased; a cell that changed and has `regrow > 0` with `tick - lastTick >= regrow` emits the inverse edit (`regrow_to`) and is erased; a sunk snow cell with `falling_refill` and `snowFalling` emits `FillAir` snow at its top + 1 every `threshold` ticks until `sunk == 0`.
6. **Tracks** (D8, 2.5).
7. **Cap**: at most `edits_per_tick` voxels leave the step; the rest wait for the next tick (the cells keep their state, the walk order is fixed).

The edits go through `wearEdits_.submit(tick, 0, EditOp::setVoxels(list))` with `EditMode::Replace` for materials, `FillAir` for refills, `PaintState` for tracks; `DestructionSystem::tick` flushes `wearEdits_` right after `fireEdits_` with `journal = nullptr, side = nullptr` and feeds the `ChangeSet` to `liquids_->onChanges` and `physics_.bumpChunks` (a sunk snow voxel under a crate: the crate must wake) and `lodPending` (the far levels see a path only after a few hundred cells: the slow set `lodSlow` is right for it). No detach analysis for material swaps (`structural_` is not fed): a swap of grass for dirt moves nothing; a sunk snow voxel is one voxel of air under a body the physics handles, not a structure.

Cost: 8 walkers x 9 cells = 72 map updates, 64 voxel edits, one small flush: well under 0.1 ms. The brick pool does not grow: a grass voxel turning into dirt inside a brick whose palette already has dirt is a re-encode into the same class (`brickEncode` reuses the slot, brick.hpp:49); a new palette entry moves a brick one class up at most once.

### 2.4 Determinism, hash, save, net, replay (the questions asked, answered one by one)

- **Deterministic**: inputs are simulated positions (never the live local player in net mode: `simP0()`), integer cell keys, fixed visiting order, fixed caps. No wall clock, no GPU. The decay uses the tick, not `dt`.
- **Hash**: `WearSystem::stateHash()` = splitmix over the cells sorted by key (key, count, lastTick, rowIndex, sunk) and the tracks in ring order; mixed into `sessionHash` when `cells_` or `tracks_` is not empty (the pattern of `events.stateHash()` at main.cpp:2246, so a project with wear off hashes exactly as before).
- **Save**: `<project>/.state/wear.bin` (`#version 2` header line of the text kind is for text files; this one is binary: magic `VXWR`, `kSaveVersion`, the counts, the records; LZ4 is not needed at 1 MB). Written with the world save (`saveAll` at main.cpp:1442, 6947, 7908, the autosave at 7767), read at start before `on_start`. A newer version is refused and kept, as docs/SAVES.md requires. Copied into a recording's `.clip` as `wear_0.bin` and read from there by a replay (the pattern of `store_0.json`). Its identity goes into the replay header (`wear` = hash:count) so a replay against another file is refused like the store at main.cpp:630.
- **Net**: the file is the host's; a joiner receives it with the world save (whatever the late-join path already sends for the store: NETWORK.md says the store travels; wear.bin goes the same way, or the session refuses to start with wear on until that exists, with a clear message). The descriptor (main.cpp:2732) gains the wear table's hash and the setting.
- **Replay**: nothing new in the log except `snow` (3.4) and `wear_clean` (2.6). The counters are rebuilt by replaying the movement.
- **Undo**: D9. Additionally `WearSystem::onChunksReplaced(chunks)` (the hook fire has, fire_system.hpp:36): cells whose chunk was swapped by an undo or redo re-read their top voxel at the next visit; a cell whose voxel is no longer `from` and not `to` is dropped (the world under it was rebuilt by the user).
- **Eviction**: a cell in an unloaded column is kept (it is state, 8 bytes) and skipped by the decay slice until the column is back; `edits` for it are not produced (the top read says `Unloaded`). A path therefore pauses while nobody is near, which is also right.

### 2.5 Tracks (the inverse)

Per walker a `load[3]` (mud, snow, sand). A stamp on a `pickup` surface: `load[class] = min(1, load + pickup)` (mud needs `coverWet > 0.3` or the surface to be dirt; dry grass gives nothing; the wetness is `rainOn`-driven and render-only today: use `rainOn` itself and a sim-side `wet` counter that rises for 60 s after rain, kept in the system). A stamp on a `deposit` surface with `load x deposit >= 0.05`: the voxels of the print get `PaintState` with the palette index of `track` (the project's palette, docs/PAINT.md; a missing name is reported once and the row is skipped), the previous state byte is remembered in `tracks_`, `load -= load x deposit`. The print shape: players and agents an ellipse of 5 x 8 voxels across the heading (the heading is simulated state); a wheel `wheelWidth x 2` voxels along the wheel's forward; a body its contact points, 1 voxel each. The age advances every tick (x `wash` while it rains); at `fade` the voxel gets its previous state back (`PaintState` with the old index) and leaves the ring. A ring that is full restores its oldest entry first.

Cost: one voxel edit per print voxel, at most 40 per step, capped by `edits_per_tick` with the wear edits (tracks after wear in the order). A painted voxel's brick gains a palette entry: with 32,768 tracked voxels in at most about 2,000 bricks moving one class up, the pool grows by at most about 2 MB and comes back when the tracks fade.

Why paint and not a decal: paint is in the brick, so it is in the hash, the save and the replay for free, the shader draws it already, and an undo swaps it with the brick. A decal layer would be a second render-only system to keep in step.

### 2.6 Actions and tools

- `wear_clean` (logged; numbers `x0 z0 x1 z1`, voxels; text empty): every track voxel inside the box is restored now, every wear cell inside is erased (the voxels stay as they are: cleaning a path means the dirt stays dirt until it regrows). Net: allowed (it is deterministic). MCP `wear_clean {min, max}`; Lua `wear.clean(x0, z0, x1, z1)` (metres, like `edit.*`) through `scriptHost` into `act("wear_clean", ...)`.
- `wear_info` (MCP, read-only): the setting, the table rows that loaded, the cell and track counts, the caps, the cost of the last step.
- `snow` (3.4).
- The Foliage window gets nothing; a "Wear" section in the Settings panel shows the two switches and the counts (no table editor in this round: the table is edited in the file and hot-reloaded like materials, main.cpp:7882 pattern, off while recording).

### 2.7 The undo journal (the hard constraint, and the soak)

Nothing in sections 2 and 3 is journaled or side-recorded, so the design adds nothing to the journal. For the open soak item (docs/TASKS.md:88) the facts in 1.11 point at the measure: `Journal` should cap **words**, not slots (`retainedBricks()` becomes `retainedWords()` summing `kClassSlotWords[pool.classOf(ref)]`, the default cap 64 M words = 256 MB, `trim` and the side recorder's `cap / 8` the same), with a test that fills the journal with class-4 bricks and checks the pool stays under the cap. That is a small change, outside this design's scope, and the builder can do it first if the soak must be green before the wear work starts (the wear soak of 8.4 needs the baseline anyway).

### 2.8 Painted cover on worn ground

A painted type (typed mask) grows on any surface (foliage_ground.comp:104). So a painted meadow would keep its blades over a path. Fix on the GPU side: the surface table (`kCoverSurfaces` x 2 words, ground_cover.hpp:135) gets a flag bit "bare" per material (set by `packCover` for `mat::Path` and for every material the project lists in a `@bare,path,gravel` line of foliage.csv); the paint branch multiplies the painted density by 0 on a bare surface. One line in the shader, one word in the pack, a GPU test (8.3).

## 3. (1) Snow: real and weather together

3.1 **Sound?** Yes, because the two never share state: the voxels are simulation, the layer is a picture. The only coupling is the picture *reading* the voxels (what it already does for every surface) and the simulation reading the `falling` flag (3.4). The user's worry "do they fight" reduces to three rules on the GPU and one table row.

3.2 **GPU rules** (foliage_ground.comp, ring 5; foliage.glsl `foliageSnowCube`):
- The first sky hit is a **snow voxel**: draw the layer at **half depth** (powder on packed snow) and keep the dents (the press map): a trodden lane on a snow field shows both the render dent and, after the sim's `sink`, a real step down.
- The first sky hit is water or ember or char: no layer (as today).
- The top voxel is a snow voxel **and** it is not snowing (`fsnow.y == 0`) **and** the amount is 0: nothing to draw (as today: the layer only exists while `fx.snow` says so). A winter biome without weather snow shows plain snow voxels, which is right.

3.3 **Compression in real snow** is the `snow, sink` row of wear.csv (2.1): six stamps sink the top voxel by 6.25 cm, the next six the next voxel. With `falling_refill = 1` a sunk cell fills back one voxel per `threshold` ticks while it snows. The sinking cell stays in the map (it holds `sunk`), bounded like the rest. A footprint that is only *rendered* (the press map) costs nothing and fades in 17 s; the sim's step is what stays and what the player collides with.

3.4 **The `snow` action**: `fx.snow(amount, falling)` keeps setting the render state **and** becomes a logged action `snow amount falling` applied like `rain` (main.cpp:1428): `snowFalling = at(1) > 0.5` is read by `WearSystem` only. The amount stays render-only (nothing in the simulation needs it). Replays and peers get it from the log, the MCP `screenshot` keeps its `snow` argument (render-only, unchanged). Determinism note: a script's `fx.snow` was not logged so far because the script is in the recording; the action is still right because the MCP tool `lua` runs ad hoc code (`lua_adhoc`), and an action is the cheapest way to make the sim flag reach every peer.

3.5 **Accumulation** (new snow on bare ground while it snows, in the simulation): **not built**. It would be a sweep of every exposed top face in the loaded area (5,329 columns x 4,096 columns of voxels = 21 M reads) or a per-chunk mask of "exposed top faces" kept in step with every edit, and its edits would rewrite every surface brick of the window (hundreds of MB of pool churn, far levels re-derived). The picture already does it (the layer); a winter *world* comes from the biome (4.2: a `season` input to the biome table at generation time, or a `snow_line` height). If the user wants snow that *stays* after a storm, the cheap version is a Lua or MCP call `edit.snow_cover(box, depth)` (one `setVoxels` of the top faces of a box: a logged action, undoable) rather than a per-tick system.

3.6 **Saved, hashed, dug**: snow voxels are world content: nothing to add. A player digs snow with the existing tools; a snowball is `emitter.grains(mat::Snow)` which already settles as snow voxels (design.md 625).

3.7 **Height-field snow in the resolve pass** (D2, the plan for later): the ground pass writes, for layer 5, only the depth per cell into a 384 x 384 R8 image (it already computes it); `particle_resolve.comp` (which already walks the near field per pixel) lifts the hit point of any top face by the bilinearly sampled depth along the surface normal, with the dent and drift from the same inputs, and writes the snow material and normal into the G-buffer; the snow splat (layer 5 in `foliage_splat.comp`) is skipped. Cost: a texture fetch and a few ALU per pixel, about 0.3 to 0.5 ms at 1440p against 1.2 ms today; the look is a smooth blanket (better) but the cubes' "sparkle" goes (a matter of taste). Effort 1.5 days with the GPU test "a snow type lies on stone and on grass" kept green. Trigger: when snow is in a shipping level and the frame budget asks for it.

## 4. (3) World generation: biomes, caves, structures

### 4.1 Shape of the change

`WorldGenParams` gains `kind` (`Demo`, `Flat`, `Biomes`), `std::shared_ptr<const BiomeTable> biomes`, `bool caves`, `int caveFloor`, `bool endless`. `WorldGenerator` keeps its interface (`generateChunk(world, chunk, col)`, `topChunkY`, `inBounds`, `landmarks`) so the streamer, the far levels, the tests and `generateWorld` do not change. Inside, the terrain function and the feature source are chosen by `kind`:

| | Demo | Flat | Biomes |
|---|---|---|---|
| height | `surfaceNoiseHeight` as today | `baseHeight` | 4.2 |
| column voxel | `columnVoxel` as today | as today | the biome's surface, subsurface, depth, sea |
| features | the fixed `ops_` list | none | region ops (4.5) |
| caves | no | no | `caves = on` (4.4) |
| landmarks | as today | the plain's middle | the start spot: column (0, 0) |

### 4.2 The biome table (`biomes.csv`)

```
# name, temp_lo, temp_hi, moist_lo, moist_hi, surface, subsurface, sub_depth, base, amplitude, roughness, sea, trees, tree_spacing, caves, snow_line
plains,   0.3, 0.7, 0.3, 0.7, grass, dirt,  24, 400, 120, 0.50, water, oak,  112, 1, 0
forest,   0.3, 0.8, 0.6, 1.0, grass, dirt,  24, 420, 180, 0.55, water, pine, 72,  1, 0
desert,   0.7, 1.0, 0.0, 0.4, sand,  sand,  40, 390, 60,  0.35, none,  none, 0,   1, 0
mountain, 0.0, 0.6, 0.2, 0.8, stone, stone, 8,  520, 520, 0.70, water, pine, 160, 1, 760
tundra,   0.0, 0.3, 0.0, 0.5, snow,  dirt,  6,  410, 90,  0.45, none,  none, 0,   0, 0
```

- **Climate**: `temperature(x, z)` and `moisture(x, z)` are two integer fBm fields (three octaves, wavelengths 4096 / 2048 / 1024 voxels: 256 m to 64 m, seeds `seed ^ 0x7e3b` and `seed ^ 0x3c91`), 0..65535, with `temperature` lowered by the **continental height** (the current `fbm2`, so mountains are cold without a third field).
- **Pick**: the biome whose (temp, moist) box contains the point; several: the one with the smaller box area (the specific wins); none: the nearest box centre. The result is sampled once per 8 x 8 voxels (the biome does not need per-voxel detail) and the four corners' picks are compared: if all four agree the cell is that biome with `blend = 0`; otherwise the two most frequent picks and `blend` = the integer bilinear weight (0..255) of the second. Deterministic, no floats.
- **Height**: `h = base_a + (fbm x amplitude_a x roughness curve)`, and with a blend `h = (h_a x (255 - blend) + h_b x blend) / 255`. The noise `fbm` is shared (one evaluation per column cell), only the biome's `amplitude` and `base` differ, so a border is a smooth ramp between two heights, never a cliff. The ridge term of today's demo becomes the `mountain` biome's `roughness` (the ridge is added when `roughness > 0.6`).
- **Column voxel**: `surface` for `d < surface depth (2..4 by jitter)`, `subsurface` for `d < sub_depth + jitter`, stone below; water up to `seaLevel` where `sea = water`; above `snow_line` the surface is snow (a mountain top) regardless of the biome. The transition between a sand biome and a grass biome at `blend` 128 is decided by the cell's hash against `blend` (a dithered edge, 8 voxels wide): no float.
- `tundra` with `surface = snow` is the **real snow** of section 3 at generation time.
- The table is **project data** (`biomes = biomes.csv`), copied into a recording's `.clip` as `biomes_0.csv` and read from there by a replay; its hash goes into the replay header and the net descriptor. A project without the file and `terrain = biomes` gets a built-in default table (the five rows above) written next to project.cfg on the first save (the pattern of `foliage.csv`).

### 4.3 Noise cost and the per-column budget

Today a column costs about 2 ms of CPU (1.6 s x 7 threads / 5,329). The biome path adds two climate fBm (three octaves) per column cell at 1/64 the density (every 8 voxels: 64 cells x 2 x 3 octaves) and the blend: under 0.1 ms. The feature path (4.5) is the same cost as today's trees. So a biome column without caves costs what a demo column costs.

### 4.4 Caves

- **Where**: only inside `[caveFloor, hMin(column) - 8]` (so a cave never opens the surface by itself; entrances are where a **worm** channel meets a slope, see below) and only at level 0.
- **Cheese** (rooms): integer value noise sampled on a **4 voxel lattice** (per chunk 17 x 17 x 17 = 4,913 samples, `valueNoise3` at wavelength 48 voxels), interpolated per voxel with integer trilinear weights (`(a x (4 - t) + b x t) / 4` per axis); air where `n > 52000 - depthBonus` (bigger rooms deeper down).
- **Worms** (tunnels): two more lattice fields at wavelength 96 voxels, `w = |n1 - 32768| + |n2 - 32768|`; air where `w < 2600` (the width in voxels follows from the gradient; about 3 to 5 voxels, which is 20 to 30 cm: too thin). Use the **8 voxel lattice** for the worms and a threshold of 9000 for tunnels about 2 m wide. Worm channels may reach `hMin - 8`; a tunnel that ends there is an entrance only when the slope is steep (the cell's `hMax - hMin > 24`): that is a per-column test in `prepareColumn`, so entrances appear on hillsides, as they do in nature.
- **Water**: a cave voxel below `seaLevel - 40` is water (a flooded cave) instead of air: it uses the liquid system's bricks when it streams in; cap it with `caves_water = 0` in the table for projects whose liquid budget is tight.
- **Cost**: per cave chunk 4,913 + 2 x 729 lattice samples (about 0.3 ms) plus 262,144 interpolations and compares (about 0.6 ms): about 1 ms, versus 0.3 ms for a terrain chunk. A column has a cave band of about 6 to 10 rows (from `caveFloor` 128 to the surface at 400 to 700): 6 to 10 ms per column, 3 to 5 x today. Walking (5 m/s) needs about 75 new columns a second at radius 36: 0.75 CPU seconds a second: one worker. Flight at 50 m/s needs ten times that: the lockstep tick waits (streaming.cpp:191: it yields until the job is done) and the frame rate drops in flight over caves. Mitigation that keeps the chunk pure: the lattice is 8 voxels for the cheese too when `caves_detail = low` (a setting of the project, not of the machine: the world must be the same on every machine). The far levels never carve (a majority vote would fill them anyway).
- **The brick pool**: a cave chunk is bricked instead of uniform stone: 1,169 bricks per column today become up to 3,000 in cave columns, so radius 36 over caves is about 350 MB of pool instead of 150. The pool is 1 GB; `lockstepMaxColumns` (main.cpp:644) still bounds the lockstep path; the 90 % gate bounds the other.

### 4.5 Structures by region

- A **region** is 512 x 512 voxels (32 m) in XZ, keyed `(rx, rz)`. `regionOps(rx, rz)` is a pure function: `hash3(rx, kind, rz, seed)` decides, per structure kind, whether and where (jittered inside the region) it stands; the biome at that point and the slope (`terrainHeight` at four points 8 voxels apart) decide if it may. Trees: today's two ops per tree, `tree_spacing` from the biome table (a region holds `(512 / spacing)^2` candidates). Later kinds (a ruin, a kit prefab from `assets/prefabs` as `EditOp::setModel`) go in the same list; a prefab's voxels make the world depend on the model file, which is project data the recording does not copy: note it in docs/SAVES.md and copy `.vxm` files a generator uses into the `.clip` like the script (small).
- **Routing**: a chunk at `(cx, cz)` asks for the ops of the regions `(cx x 64 - 256 .. cx x 64 + 320) / 512` in each axis (the 3 x 3 regions around it: a tower 192 voxels wide placed at a region's edge reaches 192 voxels into the neighbour; a structure may not be wider than 256 voxels, enforced by the kinds). `regionOps` is memoised in a bounded `std::unordered_map` guarded by a mutex (the generator runs on the job system): 1,024 regions (64 x 64 x 32 m = 2 km square), evicted in insertion order (it is a cache: a miss recomputes the same list).
- **Determinism**: the order of ops inside a chunk is `(tick, source, seq)` as today, with `source = hash of (rx, rz, kind)` and `seq` the index inside the region's list, so the order never depends on which chunk asked first.
- The far levels get `scaleOpToLevel` of the same lists (trees drop at level 2 as today).

### 4.6 Coarse levels

Levels 1 and 2 sample the biome and height at the coarse voxel's centre (as `prepareColumn` does with `S`), no caves, the scaled region ops. The existing test "coarse levels of detail are generated and reasonably consistent with level 0" (test_streaming.cpp:114) runs against the biome path too (8.1).

### 4.7 No Lua in the generation core

Reasons, in the order they matter: (1) the generator runs on the worker threads, chunk by chunk, and must be a pure function; a Lua state is single-threaded and would serialise 7 workers behind one interpreter (a column would cost 10 to 50 ms instead of 2); (2) the world would depend on the script's exact text and version, so every replay, every save and every late joiner would need the script in the state it had when the world was first generated (a save that was made with script v1 and opened with v2 would show a different world under the same edits); (3) the instruction limit and the sandbox would have to become per-chunk budgets, and a script error would have to be a "stone chunk" instead of a message. What replaces it: the biome table (data), the region kinds (C++ with data parameters), and later a **main-thread region hook** `worldgen.on_region(rx, rz, biome) -> {structures}` called once per region at request time and memoised in the same cache: deterministic because its inputs are integers and the script is in the recording; the call happens on the main thread before the column is launched (the lockstep's request tick), so it costs a few microseconds per region and never touches a worker. Not in this round.

### 4.8 Verification tools

- MCP `biome_map {centre, size_m, step}` writes a top-down PNG (`writePng`): colour per biome (from the table's surface material colour), height shading from `terrainHeight`, water in blue, cave entrances (the slope rule) as dark dots; computed on the CPU by sampling the pure functions, no chunks: 1,024 x 1,024 samples in about 50 ms. Returns the path and the biome shares (a histogram) as JSON, so an agent can say "too much desert" without looking.
- `screenshot` as today for the close look; `describe` already names the materials around.
- `check_project` learns the biome and wear tables (unknown materials, empty tables, a `terrain = biomes` without a table).

## 5. (4) Endless world and streaming

### 5.1 Columns or stacked chunks: the answer for this engine

The world is stacked chunks (`Chunk` at `(cx, cy, cz)`, world.hpp:9), but **residency is by column** (1.3). A column at radius 36 costs about 3 bricked chunks and 4 or 5 uniform ones (1.1); the empty rows above cost nothing on the CPU. So an ellipsoid or a cylinder with a small vertical radius would save, in the brick pool, only the chunks of a column that lie far above or below the player: on flat terrain nothing (the terrain band is at the player's height), under a mountain with caves the cave rows (4.4: up to 2,000 bricks a column), near the tower or the planetoids the tall features. It would **cost**: (a) the tower's top and the planetoids, which are 560 to 1,120 voxels above the ground, would not be loaded (the far levels hand over in XZ only, march.glsl:286 "height is unbounded": a Y handoff in the march is new work); (b) the generation cost does not fall, because `GenColumn` is per column and the terrain band is where the work is; a cave-only vertical cut saves the cave rows' generation but those are also what the player wants to see when standing at a cave entrance looking down; (c) every column-keyed structure in 1.3 would become chunk-keyed: `residency` (the edit queue's deferred logic relies on `ResidentEmpty` versus `Unloaded` per *column*: edit.cpp:596), `adoptColumn`'s deferred replay, `saveAll`, `stateHash`, the lockstep `pending_`, `LodUpdater::edited_`, the tests at test_streaming.cpp:152..368: about 4 days with the GPU side; (d) the **uniform pop distance** would be worse, not better: a column pops in as one, a stack of chunks pops row by row.

Where the vertical window does pay is the **GPU record table** (1.2: 350 MB allocated for 164,268 records of which about 40,000 are used). That table can shrink **without changing residency**: `dirDims.y` only needs to cover the rows that *exist* (empty chunks have no record). 5.4 designs that as a later step.

**Recommendation**: columns stay (D14); the loaded set becomes a disc (5.2); the vertical cut, if ever, is on the GPU table and on the cave band (`caveFloor`), not on residency.

### 5.2 The disc, the order, the column cache

- `cheb` (streaming.cpp:125) becomes `dist2` (squared Euclidean, integer) against `radius^2` for membership and `(radius + evictMargin)^2` for eviction; `rebuildQueue` walks the square and keeps what is inside the disc. The same reach costs 21 % fewer columns (pi / 4): 4,185 instead of 5,329 at radius 36, so the same pool and GPU table reach 40 chunks instead of 36 for the price of 36 (a free pop-in gain, 6.2). `lockstepMaxColumns` uses the disc's area. Fixed-size worlds get the disc too (the picture at the corners of the square was never seen: the level-0 box in the renderer is `radius - 2` square, main.cpp:927; make it the disc's inscribed square, unchanged, or a radius test in `boxSpanXZ`: unchanged in this round: the corners beyond the box are drawn by level 1 anyway).
- The request order is by distance already (streaming.cpp:159); add the **velocity look-ahead** of 6.1 to the centre, not to the order.
- `GenColumn` is already the per-column sample cache; with biomes it holds the biome cells too (4.1). A second cache across columns (heights of the neighbour rows for the slope tests of 4.4 and 4.5) is not worth it: `terrainHeight` is 6 octaves of integer noise, 40 ns.

### 5.4 The vertical window (later, E4)

Goal: the GPU record table from 350 MB to about 100 MB at radius 36. `dirDims.y` becomes `rowsVisible` (16: 1,024 voxels, 64 m) and the window origin's y follows the camera's chunk row minus 6; chunks outside the window exist on the CPU but have no record (`GpuWorld` skips them like empty ones, and re-registers them when the window moves: the dirty list already handles a chunk entering). The ray march needs a **Y handoff**: `boxSpanXZ` becomes `boxSpan` with a Y range for level 0 only (levels 1 and 2 keep all heights: their windows are 27 / 8 and 27 / 64 rows, small). Effort 3 to 4 days with a GPU test (the tower's top seen from its foot is level-1 voxels: a known coarse look that the test accepts). Do it when a project's memory report says the record table is the problem; in the meantime a project can lower `radius`.

### 5.5 Feature placement without a fixed origin

Region ops (4.5) are keyed by region coordinates, which are signed: a region at (-3, 7) is as good as (3, 7). The hashes take `i32`. Nothing in the biome path refers to `W / 2`.

### 5.6 Float precision far from the origin

`float` has 24 bits of mantissa: the resolution at distance `2^k` m is `2^(k - 23)` m.

| distance from the origin | resolution of a `Vec3` position | what shows |
|---|---|---|
| 1 km | 0.06 mm | nothing |
| 8 km | 0.5 mm | nothing |
| 16 km | 1 mm | nothing a player sees; the contact solver's split impulse works at this scale |
| 65 km | 8 mm (1/8 voxel) | resting bodies jitter, a capsule on a slope drifts |
| 260 km | 3 cm (half a voxel) | collision breaks |

So the first endless step is good to **16 km** from the origin in any direction (a 32 km world), with a log warning once at 16 km. The agents hold positions in **voxel units** (agent_system.hpp:75): 16 km is 262,144 voxels = 2^18, resolution 2^-5 voxel = 2 mm: the same limit.

### 5.7 The floating origin (later, E3)

When the host's simulated player crosses a 4,096 m cell boundary, every float position holder subtracts the cell's offset: `Player` (pos, the capsule's contacts), `PhysicsWorld` bodies (pos, the sleep anchors, the contact cache, the weld targets), `VehicleSystem` (chassis and wheels: bodies), `AgentSystem` (pos, waypoints), `GrabSystem` (the held point), `GravitySystem` (field centres in metres, the baked regions in voxels: integers, fine), `ParticleEmitter` (the GPU particles live in the level-0 window frame already: fine), `EmitterSystem` (positions), `EventSystem` (voxels: fine), `Renderer` (`DVec3` camera: fine), the audio listener. The shift is a simulation step at a known tick (every peer does it at the same tick, the hash is computed after it), so replays and the net stay in step. The world's integer coordinates never shift (`IVec3` is good to 134,000 km); only the metres do. Effort 3 to 4 days, half of it tests (a body at rest 20 km out must not move when the origin shifts under it; a recording that crosses a boundary replays). Do it when a project really walks past 16 km; it is listed so the limit is known, not hidden.

### 5.8 Save size and the store

`ChunkStore` appends every save of an edited chunk (chunk_store.cpp:175) and keeps the last record per coord; a long endless session with wear on rewrites the same chunks every autosave (every 300 s). The save (`.vxs`) grows by the chunk's size each time (about 20 KB compressed for a bricked chunk): 100 worn chunks x 12 saves an hour = 24 MB an hour. Two measures, both outside this round: **compaction** on open when the file is more than twice the live records (rewrite the file from `mem_`: 20 lines, the version header kept), and **region files** (`world/r.X.Z.vxs`, 32 x 32 columns each) so an endless world's save is many small files and the open does not read 1 GB. The recording's `.clip` copy of the store is capped at 256 MB already (main.cpp:614).

### 5.9 Net

Peers already stream around the union of centres (`setExtraCentres`, streaming.cpp:132; main.cpp:2671) and `lockstepMaxColumns` bounds the total for six players. Endless changes nothing there. The descriptor gains `world = endless`, the biome table's hash, the wear table's hash and the two settings. The floating origin (5.7) is per session (the host's cell), so players more than 16 km apart would lose precision: a documented limit (the fence: the session refuses a teleport that puts a player more than 12 km from another).

## 6. (5) Pop-in

6.1 **Load ahead along the velocity** (the default): the streamer's centre is `camChunk + clamp(velocity x 2 s, 6 chunks)`, computed from the simulated player's velocity (deterministic) in lockstep mode and from the camera in `update()` mode. A walker at 5 m/s looks ahead 2.5 chunks; a vehicle at 20 m/s the full 6. Cost: nothing. Measured as the number of frames a column was visible before it arrived (a counter in the streamer's stats: `lateColumns`, columns adopted inside `radius - 4` of the current centre).

6.2 **A bigger radius for the same budget**: the disc (5.2) gives 40 for the price of 36. The brick pool is not the limit (150 MB of 1 GB); the GPU record table is (1.2). `radius` stays a setting.

6.3 **Dithered cross-fade at the level boundary** (`lod_fade = off | on`, off by default): in `raymarch.comp` a pixel whose level-0 hit lies within 12 chunks of the box edge is marched a second time on level 1 with probability `(d - (box - 12)) / 12` (a per-pixel blue-noise threshold, the one TAA uses), and the TAA resolves the dither into a fade. Cost: the second march for a band of about 15 % of the ground pixels at 1440p, 0.4 to 0.8 ms on the RTX 3070 (the march is 8 to 14 ms for the whole frame, docs/TASKS.md:60). Design.md:273 asks for exactly this ("dithered over 20 m"); it is off by default because the measured cost decides.

6.4 **Fog at the box edge** (free, on by default when `lod_fade` is off): `fogDensity` already exists (renderer.cpp:762 `P.misc[1]`); the shade pass adds a distance term that starts at `boxHalf - 8 chunks`, so the level handoff lies in the fog. A setting `fog_edge = 0..1` for projects whose look wants a clear horizon.

6.5 **Priority order**: already nearest first; with the look-ahead the "nearest to the look-ahead point" is right for walking; for a camera that turns quickly (third person, top-down) the view direction is not useful, the velocity is.

**Measure plan** (needs the real GPU): the tour script of the nightly (`tour_seed`) with a counter of late columns and the GPU frame time, before and after each of 6.1, 5.2, 6.3; the acceptance is "late columns 0 at walking speed, under 5 % at flight, frame time within 1 ms of today".

## 8. Tests and gates that keep today's worlds exactly as today

8.1 **Bit-identical demo and flat worlds**: a unit test generates the 32 x 32 demo world and the flat world with today's parameters before and after each generator commit and compares `World::contentHash()` (test_streaming.cpp:90 already fixes the hash of a generated window: extend it with the two hashes as constants). The replay logs of `tools/determinism.sh` are recorded against the demo world, so a changed world fails the nightly anyway; the unit test fails earlier.

8.2 **Settings off means nothing changes**: `sessionHash` mixes the wear state only when it is non-empty (D18), the queue is not flushed when `wear = off`, and the `snow` action exists but sets a flag nobody reads: a recording made before W1 replays unchanged. The nightly's existing recordings prove it.

8.3 **GPU tests on llvmpipe**: the snow-on-snow rule, the bare-surface rule for painted cover (2.8), the dirt tint of a worn path, the fog edge. They follow the pattern of the foliage tests (a fixed scene, a camera, a count of pixels of a colour).

8.4 **The soak**: `--soak` with `--setting wear=on --setting tracks=on` and the walking script: the pool slope must stay under the limit (with W0 the limit means what it says).

8.5 **Net**: `tools/net_test.sh` with wear on: two peers, hashes agree every 60 ticks (the wear hash is in the session hash).

## 10. Ideas that fit (not in the order of work)

- **Region-based save compaction** (5.8): `world/r.X.Z.vxs` files of 32 x 32 columns, each rewritten when it has more than twice its live records; a `--compact` command and a line in `check_project`.
- **Chunk compression at rest**: the store keeps LZ4 payloads already; a column evicted and reloaded within a minute could skip the deserialise by keeping the last N evicted columns' chunks alive in a graveyard with a budget (a "warm" cache): fewer brick allocations when a player paces at the window's edge. Measure the eviction churn first (the streamer's `evicted` and `fromStore` stats).
- **A wear heat map** for the editor: the cells as a translucent overlay (the debug-draw pass), so a level author sees where the agents walk; the data is there.
- **Agents and wear**: an agent's navigation (nav.hpp) could prefer `path` voxels (a cost per material): paths then make themselves, which is what the user described as the goal.
- **Snow line by season**: `fx.season` is render-only; a biome's `snow_line` lowered by a logged `season` action would be a sim change of the world (a sweep, 3.5 says why not); the cheap version is the render layer's amount following the season, which the script already can do.
